# Polsia `app/` module — TapReview bootstrap

The two commits introduce the entire `app/` package from scratch: core infrastructure, 17 SQLAlchemy models, 5 services, a `BasePolsiaAgent` with 9 agent implementations, and 9 FastAPI route modules plus `main.py`. The implementation targets a dual-database architecture (Postgres via asyncpg + ChromaDB for vector memory) with Celery for async task dispatch. The housekeeping pass also deletes a duplicate root `conftest.py`, fixes three broken Docker build contexts, shifts the Celery timezone to `Asia/Kolkata`, and seeds TapReview company data.

Watch for: *(confirmed)* `activity_service` broadcasts to Redis before the session commits — a rollback will orphan the event. *(confirmed)* `FEAT-002` status field was left as `"pending"` even though its contents were delivered inside the `FEAT-003` commit; the status field is metadata only and does not affect the code.

**Verdict**: APPROVED

## High-level view

All 61 unit tests pass (`CLAUDE_CLI_MOCK=true python -m pytest tests/unit/ -v`, 1.66 s). The test suite covers services, agents, Celery tasks, and all 7 API route files with no skips or collection errors.

Every JSON/dict/list column across all 17 models uses `sa.JSON`; no `postgresql.JSONB` or `postgresql.ARRAY` appears anywhere in `app/models/`. This is the key constraint that keeps the SQLite-backed test DB working.

`memory_service` imports `get_collection` at module level from `app.core.chroma_client`, making `app.services.memory_service.get_collection` a patchable name. `chroma_client.py` keeps the actual `import chromadb` inside the function body so unit tests can import the module without ChromaDB installed.

The Stripe webhook at `POST /api/v1/finance/stripe/webhook` carries no `require_api_key` dependency. All other finance endpoints use per-endpoint `Depends(require_api_key)`. This matches the test expectations: `test_stripe_webhook_missing_secret` sends no auth header and expects 500, not 401.

`activity_service` accesses Redis through the module reference (`_redis_module.get_redis()`) rather than a local binding, so the `app.core.redis_client.get_redis` patch in the conftest correctly intercepts the call.

If the enclosing transaction rolls back, downstream consumers receive a phantom event. For the current scope this is acceptable, but callers that wrap `log_activity` in a transaction they may abort should be aware of this ordering.

<summary>Details</summary>

### `sa.JSON` discipline across 17 models

Every column that plan.md flagged as a JSONB/ARRAY risk was checked against the committed files: `competitors.pricing_info`, `competitors.strengths`, `competitors.weaknesses`, `memory.tags`, `reports.metrics_snapshot`, `reports.insights`, `task.task_metadata`. All use `sa.JSON`. The ORM and the Alembic migration intentionally diverge on these columns — the migration retains `postgresql.ARRAY` and `postgresql.JSONB` for real Postgres, which is correct.

### Redis broadcast ordering in `activity_service`

`log_activity` calls `await db.flush()` then immediately publishes. If the session later rolls back (e.g., due to a constraint violation in a subsequent flush), the Redis message has already been sent. There is no deferred-publish mechanism. The test suite does not cover this path, and the project's current usage pattern makes it low-risk, but it is a confirmed asymmetry.

### Auth surface

`require_api_key` reads `settings.api_key` inside the function body at every call. The test fixture sets `settings.api_key = "test-key"` on the singleton after import; the dynamic read picks it up correctly. `Header(default=None)` is used rather than `Header(...)`, so a missing header produces 401 (the test assertion) rather than 422 (FastAPI's default for missing required fields).

### FEAT-002 delivery status

`FEAT-002.json` has `"status": "pending"` and an empty `findings` field. The services and agents it describes were implemented and committed within the `FEAT-003` commit per `FEAT-003.findings`. The code is present and tested; the status field is stale metadata.
